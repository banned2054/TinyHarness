### 2. 保存和恢复是否都已实现？

**用户：**

> 你的意思，目前的持久化，包括储存和恢复都做了？

**助手：**

**对，目前针对 `chat` 的持久化，保存和恢复都已经实现了，不是只把运行日志写到磁盘。**

具体包括：

- **保存会话**：每个回合结束后保存完整对话和压缩状态；执行有副作用的工具前，还会先保存执行意图检查点。存储包含格式版本、原子替换、提交序号、审计对账和跨进程排他锁。
- **正常恢复**：通过 `tinyharness chat --session <id>` 重新打开，保留之前的目标、事实、工具结果及必要的协议内容，继续下一轮对话。恢复前会校验工作区、模型、协议等是否兼容。
- **中断后安全恢复**：如果上次操作可能执行了、但结果没有可靠记录，会回到最近完整的对话协议边界，并阻止继续写文件或执行命令，直到用户明确检查确认。**不会自动重放上次的工具操作。**
- **离线检查**：`session list` / `session show` 可以在不调用模型的情况下查看保存状态、运行和工具记录。

但有几个边界需要说清楚：

1. **恢复的是会话上下文，不是让被中断的命令接着跑，也不会自动回滚工作区。**
2. 可续聊的是新的 **v3 会话格式**；旧版快照和单次 `run` 的检查快照不能直接恢复成长期会话。
3. **会话文件不加密**，完整对话中可能含敏感内容。
4. 保存、重启续聊和中断确认链已做过离线测试及本地模拟服务下的原生产物验证；**真实模型续聊仍未验证**。本次只是代码核查，没有重跑测试。

所以，**M13 的存储与安全恢复主体已经完成**；接下来的 M14 是补项目 `AGENTS.md` 加载和宿主强制的只读／实施模式，不是再补一个尚未实现的恢复功能。

### 3. M7 已有持久化，M13 是否重新设计了一套？

**用户：**

> v3是啥，我记得第7阶段，似乎就已经有持久化了？虽然是不能恢复的，你的意思是13阶段重新设计了一个持久化？

**助手：**

**你记得对：M7 就已经有持久化了。我刚才说得不够准确，应该区分“运行记录的持久化”和“可恢复会话的持久化”。**

#### M7 和 M13 的区别

| | M7：运行级持久化 | M13：会话级持久化 |
|---|---|---|
| 保存单位 | 一次 `run` | 一个包含多个回合、多个运行的长期会话 |
| 保存内容 | 审计事件、脱敏后的消息、结构化状态和运行结果 | 回合记录，以及能够保真恢复的完整对话和压缩状态 |
| 主要用途 | 查看发生了什么、排错、检查结果 | 退出后续聊、中断后安全恢复 |
| 能否恢复 | 原本没有提供恢复契约 | 通过身份、协议及完整性校验后恢复 |

**M7 并不只是写日志，它已经保存了对话快照。** 但“保存了一份对话”不等于“这份数据可以可靠地重新送给模型继续运行”：脱敏可能改变内容，还需要处理工具调用是否完整、操作是否已经执行、模型协议是否匹配等问题。

#### 所以，M13 是不是重新设计了一套？

**是，M13 新设计了“可恢复会话”这一层的格式和存储机制；但没有替换或废弃 M7 的运行记录。现在两者并存。**

目前的关系可以理解为：

- **M7 的运行档案**：记录每次任务发生了什么。
- **M13 的会话档案**：把多次任务组织成一个长期会话，并保存下一次续聊需要的上下文。
- `chat` 中的每次运行仍使用原有运行记录机制，同时另存整个会话。

所以这不是“以前完全没有持久化，M13 才开始做”，也不是“给旧 JSON 加一个读取方法”，而是**在既有运行持久化之上，增加可恢复会话层**。

#### v3 到底是什么？

**v3 是 M13 新会话文件里的 `formatVersion = 3`，不是产品版本，也不是 M7 旧快照的第三版。**

它在 M13 开发过程中经历了这些变化：

- **v1**：保存会话身份、回合和运行检查记录，尚没有消息级的完整续聊内容。
- **v2**：加入消息级会话内容，但内容可能经过脱敏，无法保证无损恢复。
- **v3**：将两种用途明确分开：
  - **续聊底稿（canonical）**：原样保存必要的消息和协议字段。
  - **检查视图（inspection）**：脱敏后供终端、审计和 `session show` 查看。

关键原因就是：**不能拿一份已经把内容替换成 `[REDACTED]` 的检查稿，冒充原始上下文来做无损恢复。** 代价是原样底稿可能包含敏感内容，而且文件没有加密。

旧 M7 快照以及 v1/v2 会话文件目前仍可检查，但不会自动升级成可续聊的 v3。

相关依据见 [M7 历史计划](../../PAST_PLAN.md#15-持久化与审计) 和 [阶段计划中的存储说明](../../PAST_PLAN.md#7-持久化与安全续聊)。**准确总结就是：M7 做了“留档”，M13 在保留留档能力的基础上，新增了“跨进程接着聊”的存储与恢复体系。**

> 归档补充：后续 Git 历史核查没有找到独立提交的 `CurrentFormatVersion = 2`；可见历史直接由 1 变为 3。关于 v2 的描述来自当前兼容契约、注释与计划记录，不能据此推导它曾独立发布或独立验证。

### 4. 为什么要两份？是否在堆积技术债？

**用户：**

> 为什么要两份，这不是屎山堆积了

**助手：**

**这里确实有技术债。当前 `chat` 重复保存了对话内容，不能用“恢复需要”或“兼容旧功能”来充分解释。我前面的回答把职责区分和存储重复混在了一起。**

#### 真正重复的地方

当前 `chat` 每轮结束会走两条保存路径：

- **旧 M7 运行快照**：保存截至这一轮的共享对话历史、结构化状态和运行结果的脱敏副本，每次运行生成一个新文件。
- **新 M13 会话快照**：保存同一份对话的保真内容、压缩状态，以及各回合的运行检查记录，更新会话文件。

也就是说，不只是“日志和会话各存一份”，而是**旧运行快照里也有对话历史，新会话快照里又保存了它**。聊得越多，旧快照还会反复留下此前的历史。

实际双写入口在 [Program.cs:263](../../TinyHarness.Cli/Program.cs#L263)，旧快照写入内容见 [RunPersistence.cs:153](../../TinyHarness.Core/Services/Persistence/RunPersistence.cs#L153)。

#### 为什么会这样？

从当前实现看，M12 的多轮会话沿用了原来的运行记录器，M13 又接上了新的会话存储，**但没有拆开旧记录器里的“执行审计”和“全量快照”职责**，所以两条路径都留下来了。

保留独立 `run` 命令的旧产物，可以是兼容要求；**新 `chat` 也继续生成旧式全量快照，却不是兼容的必然要求。**

这不仅浪费磁盘，还增加了两套保存路径、错误处理和一致性维护成本。你的质疑不只是命名或审美问题。

#### 哪部分仍然合理？

“恢复用的原始内容”和“查看用的脱敏摘要”需要区分。M13 内部也不是放了两套完整消息数组，而是保真历史加脱敏的回合／运行检查记录。这有实际用途，尤其离线查看不能直接泄露原文。

**但这解释不了为什么还要额外生成 M7 的全量对话快照。**

更合理的边界是：**会话内容有一个权威存储，执行审计保留独立事实，检查输出使用脱敏视图；旧 `run` 的兼容不应迫使 `chat` 重复存整份历史。**

所以，不是 M13 的恢复能力不该做，而是**新增会话存储后，旧的重复保存路径没有收口**。这部分批评成立。本轮只是核查和评估，没有修改代码。

### 5. 是否仅保留 M13 的版本？

**用户：**

> 那么应该考虑仅保留m13的版本?

**助手：**

我会区分“统一到 M13 格式”和“删除旧记录能力”，确认哪些可以合并、哪些仍有独立价值。**是。我建议把 M13 的 v3 作为唯一的会话快照格式，停止继续维护两套全量快照。** 但要区分“淘汰旧快照实现”和“删除审计能力”。

合理的收口方式是：

#### 1. `run` 和 `chat` 共用一套持久化核心

- `chat` 保存多回合会话。
- `run` 可以按单回合会话使用同一套模型和保存机制。
- 格式校验、序列化、原子保存、执行记录等不再各写一套。

**统一实现不代表必须改变 `run` 的命令、默认输出目录或所有既有行为。** 这些属于兼容边界，不能因为内部重构就顺手改掉。

#### 2. 淘汰旧的全量运行快照，保留执行审计

旧 M7 记录器里有两种职责：

- **全量对话快照**：与 M13 重叠，应当退出默认写入路径。
- **工具准备、审批、执行结果等审计事件**：仍有独立价值，不能因为快照重复就一起删除。

最终应该是：**一份权威会话快照，加职责清楚的审计记录**，而不是两份都声称描述完整会话的快照。

#### 3. 暂时保留 M13 的脱敏检查视图

这部分有明确用途：离线查看时不读取真实凭据，也不直接暴露原始对话中的已知秘密。

它可以作为同一快照内的受控检查数据保留，**不必为了追求“绝对只存一份”再引入一套复杂的动态脱敏机制**。先消除跨存储系统的全量重复，更有价值。

#### 4. 旧文件只读兼容，不继续双写

已有 M7、v1/v2 文件不自动删除、不冒充可恢复数据。保留读取旧文件的兼容入口，并不意味着新运行必须继续生成旧格式。

所以我的建议不是“旧的先留着，新的再叠上去”，而是：**以 M13 v3 为主线完成持久化收口，把旧实现中仍有价值的审计职责留下，重复的快照写入淘汰。这比带着两套全量持久化继续进入 M14 更合理。**

### 6. 工具准备、审批和执行审计，M13 没有吗？

**用户：**

> 这部分13阶段的版本没有嘛
>
> 引用：工具准备、审批、执行结果等审计事件：仍有独立价值，不能因为快照重复就一起删除。

**助手：**

**M13 有这部分记录，但没有独立重写一套完整的执行审计；它复用了原来的审计实现。** 我之前按“M7 的能力”和“M13 的能力”来讲，容易让你以为必须保留两套系统，这不准确。

当前实际是：

| 位置 | 保存什么 |
|---|---|
| **M13 v3 会话快照** | 工具调用身份、准备摘要、授权结论、执行是否得到确认等，服务于恢复和中断检查 |
| **复用的运行审计** | `tool.prepared`、`tool.permission`、`tool.result` 等事件，以及时间、成功标记、退出码、超时等细节 |
| **M13 会话提交审计** | 快照提交序号与时间，用于检查保存一致性，不是工具执行审计 |

所以，**v3 快照已经覆盖了部分准备、审批、执行信息，但尚未包含完整的执行事件记录，不能直接替代现有运行审计。** 比如“结果已确认”不等于“执行成功”，退出码、超时等仍由运行审计独立记录。

你说“只保留 M13”，如果意思是**统一为一套持久化体系**，这个方向合理；如果直接删除旧 `FileRunRecorder`，目前会连带丢掉审计细节，因为它把“执行审计”和“旧全量快照”绑在了一起。

**准确的结论是：现有执行审计可以继续复用，不需要为了叫“M13 版本”而重写；需要消除的是它附带的旧全量快照重复写入，而不是保留两套完整持久化系统。**

### 7. 列出旧路径独有、可考虑移植的能力

**用户：**

> 这样，你说一下v1v2有哪些v3没有的功能，我再评估要不要移植给v3

**助手：**

**核对后，严格意义上的 M13 v1/v2，没有发现“旧版有、v3 丢掉了”的功能。需要考虑移植的，实际是旧 `run` 存储路径中的审计细节和少量统计。** 我前面把格式版本与新旧存储系统交叉着讲，造成了混淆。

#### 旧运行记录里有哪些信息，v3 快照没有？

注意：**这些信息目前并没有从 `chat` 中消失，而是仍保存在它复用的旧运行审计／快照里，没有统一到 v3。**

| 信息 | 旧运行产物保存什么 | v3 会话快照的缺口 |
|---|---|---|
| **结构化工具结果** | 成功标记、退出码、超时、输出裁剪标记 | 只有“结果是否已确认”的状态，以及工具返回文本，没有这些独立字段 |
| **准备后的目标与策略** | 规范化目标路径、执行策略身份 | 有原始调用参数和准备摘要，没有这两项独立记录 |
| **权限决策过程** | `Allow / Ask / Deny` 决策，以及最终审批结论 | 有审批结论，没有单独的权限决策字段 |
| **运行压缩次数** | 本次运行的 `Compactions` | 没有这个统计字段；但当前压缩状态和折叠边界已经保存 |
| **逐次模型调用统计** | 每次上报的输入／输出 token、结束原因 | 仅保存运行级 token 合计，没有逐次明细 |
| **执行与压缩事件时间线** | 事件顺序、时间，以及每次压缩前后的估算 token 数 | 有运行起止时间和最终状态，没有同等粒度的事件序列 |
| **每次运行结束时的历史版本** | 每个 run 单独留一份当时的完整脱敏历史与状态 | 更新当前会话快照，不保留每轮对应的完整旧版本 |

这里最容易误解的是第一项：**“结果已确认”不等于“执行成功”。** v3 可以知道某个调用已经收到了结果，但若要确定性地生成报告，仍需要独立的退出码、超时等字段，而不是重新解析结果文本。

依据主要在 `TinyHarness.Core/Services/Persistence/RunPersistence.cs:59` 和 `TinyHarness.Core/Models/Persistence/PersistedSession.cs:244`。

#### 我的移植建议

**建议并入统一会话记录：**

优先考虑前四项：

1. **结构化工具结果**。
2. **准备后的目标路径与执行策略身份**。
3. **权限决策与最终审批结论的区分**。
4. **运行压缩次数**。

这些属于明确的执行事实和统计，适合与 v3 的运行／工具记录放在一起，也能为之后的验证报告提供依据。保存审批事实，**不代表恢复旧授权**。

**适合继续作为审计明细：**

- 逐次模型 usage 与结束原因。
- 执行事件时间线、压缩过程。

它们有价值，但**统一持久化体系不等于必须把所有事件塞进一个快照 JSON**。可以由同一套存储管理会话快照和关联审计，避免重复保存完整对话。

**不建议原样移植：**

**每轮都保存一份完整历史快照。** 它有历史诊断价值，但也正是目前重复存储的主要来源。除非明确需要历史版本检查，否则不应为了保留这个副产品，继续逐轮复制整段对话。

另外，完整工具输出 artifact 的长期归档，**新旧两边都没有完整保证**，不能算作旧版可直接移植的能力。

**因此，真正值得你评估的核心是前四项执行事实；不是把 v1/v2 整套搬回来，也不是把旧全量快照塞进 v3。** 本次仅做了只读对照，没有修改代码。

#### Codex 的方案值得借鉴在哪里？

我核对了它当前公开 `main` 的实现，核心不是“把所有东西塞进一个文件”，而是清楚地区分几种职责：

**1. 会话记录与恢复围绕同一条历史展开**

Codex 使用追加写入的 **rollout JSONL** 保存会话记录，恢复时读取这些记录重建上下文，然后继续追加。

这与 TinyHarness 当前“每轮另写一份完整旧运行快照，同时更新新会话快照”不同。值得借鉴的是：**不再逐轮复制整本对话，而是明确记录会话如何发展。**

源码：[recorder.rs](https://raw.githubusercontent.com/openai/codex/main/codex-rs/rollout/src/recorder.rs)

**2. 磁盘历史不等于下一次发给模型的上下文**

压缩之后，模型使用的有效历史可以改变；恢复逻辑能够识别压缩记录和替代历史，重建当前应该使用的上下文。

这让“历史留档”和“模型上下文预算”不必靠两套全量快照解决。这里的重建是**恢复数据状态，不是重新执行旧命令**。

源码：[rollout_reconstruction.rs](https://raw.githubusercontent.com/openai/codex/main/codex-rs/core/src/session/rollout_reconstruction.rs)

**3. 展示、索引与执行审计不混为一谈**

Codex 并非把所有界面事件都持久化，也不是只有一个文件；它还有索引和 SQLite 状态存储。

因此，真正应当追求的是：

> **每类事实由哪里负责、哪些数据由它派生，要明确；不是机械地追求“只能有一份文件”。**

同时，Codex 的 rollout 也不能直接当作完整的安全审计日志，它会筛选持久化事件。

源码：[policy.rs](https://raw.githubusercontent.com/openai/codex/main/codex-rs/rollout/src/policy.rs)

#### 对 TinyHarness，我的判断是什么？

**可以借鉴 Codex 的整体记录与恢复模型，而不是把 M7 的功能逐项搬进 v3。** 这样讨论的重点就从“缺几个字段”变成了：

- 会话历史和执行事实如何统一关联。
- 压缩后如何恢复有效上下文。
- 检查输出如何脱敏。
- 如何消除逐轮复制完整历史的旧路径。

但有两点不能因为对标 Codex 就丢掉：

- TinyHarness 已有的执行意图检查点、未知副作用阻断和明确确认机制。
- .NET、NativeAOT、严格离线查看等项目约束。

也不需要把 Codex 的 SQLite、所有事件类型和 Rust 模块组织照搬过来。**应该移植它经过实际使用验证的行为和清晰的数据职责，而不是复制它的全部复杂度。**

这些判断依据的是公开源码，不代表你正在使用的那个发布版，也尚未证明换一种持久化就能复制全部使用体验。不过，**以 Codex 为明确对标，重新确定持久化契约，比围绕当前 v3 零散补功能更有一致性；我支持这个方向，而不是默认继续保住现有两套实现。**

#### 一、Codex 真正值得借鉴的结构

**1. 会话历史以追加记录为主，不是每轮重存整本对话**

它的核心存储单位是 `RolloutItem`，包括：

- 会话元数据。
- 模型消息、工具调用和工具结果。
- 回合上下文。
- 压缩检查点。
- token 使用记录。
- 筛选后需要持久化的运行／展示事件。

这些记录写成 JSONL。正常运行追加新记录，恢复后继续写，而不是每轮结束都生成另一份截至当时的完整聊天快照。

依据：`C:\Code\Rust\codex\codex-rs\history\src\lib.rs:214`、`C:\Code\Rust\codex\codex-rs\rollout\src\recorder.rs:1048`。

**这正好对应 TinyHarness 当前最应该消除的问题：旧 run 快照逐轮复制完整历史，同时新 session 快照又保存同一历史。**

但“追加为主”不等于永不重复内容。压缩检查点可以包含一份替代上下文，这是为了恢复效率而有明确用途的重复，不是另一个系统再独立维护整份会话。

**2. 历史档案、模型上下文、界面历史各有职责**

这是我认为比“用 JSONL 还是 JSON”更重要的设计。

Codex 并没有强迫三者使用完全相同的数据形态：

| 职责 | Codex 的处理 |
|---|---|
| **保留会话记录** | 保存协议项、必要运行事实和压缩记录 |
| **恢复模型上下文** | 从存活的压缩检查点及后续记录重建 |
| **恢复界面历史** | 从回合和完成的展示条目投影，并支持分页 |

新的界面历史投影明确忽略 `ResponseItem`，主要使用回合生命周期和 `ItemCompleted`；模型恢复走另外的上下文重建路径。

依据：`C:\Code\Rust\codex\codex-rs\app-server-protocol\src\protocol\thread_history_projection.rs:20`。

**因此，Codex 也会保存内容有所重叠的协议记录与展示记录。区别在于用途明确，而不是“只要有重复字段就是设计错误”。** 我之前对“两份”的批评需要限定在 TinyHarness 两条全量快照路径上，不能扩大成否定所有投影。

**3. 压缩是可恢复的上下文检查点**

当前格式可以保存 `replacement_history`，也就是压缩后应当使用的上下文。

恢复时，大体上是：

1. 找到仍然有效的压缩检查点。
2. 用它的替代历史作为基础。
3. 加上检查点之后仍然有效的记录。
4. 重建模型上下文，而不是重新执行工具。

新分页格式还可以从后向前扫描，只读取恢复所需的检查点和后续部分，不必每次加载全部历史。

依据：

- `C:\Code\Rust\codex\codex-rs\history\src\lib.rs:289`
- `C:\Code\Rust\codex\codex-rs\thread-store\src\local\model_context.rs:27`
- `C:\Code\Rust\codex\codex-rs\core\src\session\rollout_reconstruction.rs:492`

**这比不断重写“完整历史＋当前压缩状态”的大快照，更适合长期会话。**

#### 二、旧运行记录里值得保留的细节，Codex 如何处理？

Codex 新分页格式会保存结构化的完成条目。以命令为例，条目包含：

- 命令和工作目录。
- 执行状态。
- 合并输出。
- 退出码。
- 耗时。
- 条目身份。

因此，**执行事实不必依附于旧全量聊天快照才能留下来**，可以作为同一会话记录中的结构化条目保存。

依据：`C:\Code\Rust\codex\codex-rs\protocol\src\items.rs:251`。

不过，它也不是“什么都保存”：

- 审批请求、输出增量等瞬态事件不会按原样全部落盘。
- 新分页格式的命令展示输出有 **64 KiB** 持久化裁剪。
- 部分仅用于实时分析的字段不会序列化。
- rollout 不能直接等同于完整安全审计日志。

依据：`C:\Code\Rust\codex\codex-rs\rollout\src\policy.rs:126`、`:249`。

这说明我们可以借鉴它的结构化执行条目，但仍需按 TinyHarness 的要求明确保留审批、策略身份和未知执行状态等事实，不能只复制字段表。

#### 三、哪些不能照搬？

**1. 缺失工具结果的处理，与 TinyHarness 当前契约不同**

Codex 在构建模型请求的历史视图时，会对缺失结果的部分工具调用补入 **`aborted` 占位结果**，使协议配对完整。

这不是补造成功，也不表示命令没有产生副作用；它是对模型输入的归一化处理。

TinyHarness 当前选择的是：

- 不完整尾部工具组整体回退。
- 独立保留执行事实。
- 未知副作用触发 `NeedsInspection`，用户检查确认前阻断后续副作用。

**不能因为采用 Codex 的日志结构，就顺手把 TinyHarness 的中断保护替换成占位结果。**

依据：`C:\Code\Rust\codex\codex-rs\core\src\context_manager\normalize.rs:21`。

**2. “记录完成”不能直接当作“执行前安全检查点”**

Codex 存储层有队列、flush 屏障和错误返回；但在所查的普通工具派发链路中：

- 记录失败可以只记日志。
- 上层记录函数不把失败继续作为执行门禁。
- 随后仍会构造工具执行任务。

所以，这条路径不等价于 TinyHarness 的“**副作用执行前必须可靠保存执行意图，否则不启动工具**”。

依据：`C:\Code\Rust\codex\codex-rs\core\src\session\mod.rs:4748`、`C:\Code\Rust\codex\codex-rs\core\src\stream_events_utils.rs:346`。

普通 JSONL 写入使用 `write_all` 和 `flush`，也不能据此宣称具备断电持久性；它不等于 `fsync`。TinyHarness 当前方案同样不能仅凭原子替换就作这种保证。

**3. 损坏记录的容错策略也不同**

Codex 的一个完整日志读取路径会跳过无法解析的记录并累计错误数，而不是遇到任何坏记录都拒绝恢复。

这有可用性上的价值，但对于执行记录，**缺失的是普通展示信息还是副作用确认事实，后果完全不同**。TinyHarness 不宜直接照搬“坏行跳过继续”。

依据：`C:\Code\Rust\codex\codex-rs\rollout\src\recorder.rs:1104`。

#### 四、SQLite 要不要一起采用？

**现阶段没有必要仅为对齐 Codex 就引入。**

而且，我之前把数据库概括为“可重建索引”也过于简单：

- 会话历史投影可以由日志重建。
- 但当前 Codex 有些元数据更新只写 SQLite。
- 某些回退操作后，当前选中的 rollout 路径也由数据库状态决定，不能靠扫描文件可靠推断。

所以不能说“删掉 Codex 数据库，所有状态都能从日志无损重建”。

依据：`C:\Code\Rust\codex\codex-rs\rollout\src\state_db.rs:560`、`C:\Code\Rust\codex\codex-rs\thread-store\src\local\update_thread_metadata.rs:157`。

TinyHarness 首先需要的是清晰的会话记录契约，不是先复制 Codex 的数据库、分页和历史分支基础设施。

#### 对 TinyHarness 的最终建议

**我支持以 Codex 的追加式会话记录为新主线，让它取代当前两套全量快照的写入，而不是成为第三套。**

具体取舍是：

- **采用**：统一会话记录、结构化执行事实、压缩检查点、从记录重建有效上下文。
- **保留**：TinyHarness 的执行意图检查点、未知副作用阻断、明确检查确认、脱敏检查输出及 NativeAOT 约束。
- **淘汰**：`chat` 每轮生成旧式完整 run 快照的重复路径；历史文件兼容读取与继续写旧格式分开处理。
- **暂不照搬**：SQLite-only 元数据、复杂历史分支、全部 Codex 事件类型和它较宽松的损坏恢复策略。

**因此，这不再是“把几个功能移植给 v3”，而是“借鉴 Codex，统一设计 TinyHarness 的会话记录与恢复体系”。v3 应当是需要被兼容读取的现有格式，而不是限制新设计的中心。**

### 10. 是否意味着要出 v4？

**用户：**

> 什么意思，v3点缝补，也不足以实现codex风格的持久化，所以要出v4？

**助手：**

**如果决定把“追加式会话记录”作为权威存储，替换当前的全量快照，那确实需要一种新格式，可以叫 v4。但不是因为 v3 功能不够，也不是 Codex 风格天然要求升版本。** 我上一条把架构调整和版本号绑得太紧了。

要分两种情况：

#### 只解决当前的重复持久化：不需要 v4

继续使用 v3，拆开运行记录器里的审计与快照职责，让 `chat` 不再额外生成旧全量快照，就能消除当前最明显的重复。

工具结果、退出码等执行事实，也可以评估以兼容方式扩充现有记录。

**这些是合理的收口，不是无意义的“打补丁”。**

#### 改成 Codex 式的追加记录与重建：属于存储架构变化

区别不是多几个字段，而是：

| | 当前 v3 | 借鉴 Codex 的方案 |
|---|---|---|
| 权威数据 | 当前会话的完整快照 | 按顺序追加的会话记录 |
| 保存 | 重写完整快照 | 追加新记录 |
| 恢复 | 读取快照中的历史和状态 | 从检查点及后续记录重建 |
| 压缩 | 保存当前状态和折叠边界 | 追加可恢复的压缩检查点 |

这种变化**无法只靠给 v3 添加字段完成**，还要调整写入、读取、恢复和故障处理。若这样改，用新格式标识区分是正确的；继续叫 v3 反而容易让读写端误判兼容性。不过，新格式编号本身不意味着项目所有模块都要重写。

**我的准确建议是：如果你的目标只是去掉重复，收口 v3 就够了；如果你明确希望采用 Codex 那种追加记录、检查点和重建模型，就设计新的存储格式替换 v3 写入。** 旧 v3 保留读取或转换能力，而不是让 v3、v4 长期双写。

所以，**“要不要 v4”应当是选定存储模型后的结果，不该先为了对标 Codex 而决定升级版本。**

### 11. v3 每次重写，Codex 追加，这是否是最大区别？

**用户：**

> 看上去v3是每次都会重新创建一个新的快照？而不是在旧的快照里写新的记录，这是和codex最大的区别？

**助手：**

**对，你抓住了最核心的区别：v3 每次保存都会重新生成完整快照，再替换原文件；Codex 的会话历史则以追加新记录为主。**

但“新快照”不代表每次都永久留下一个新文件，需要区分两条路径。

#### 当前 v3：同一个会话文件，内容整体替换

每次保存的过程是：

1. 把当前完整对话、压缩状态、回合和运行记录重新序列化。
2. 写入同目录的临时文件。
3. 用临时文件原子替换原来的 `<sessionId>.session.json`。

例如：

```text
第一轮保存：文件内容 = 第一轮
第二轮保存：文件内容 = 第一轮 + 第二轮，整体重写
第三轮保存：文件内容 = 第一轮 + 第二轮 + 第三轮，整体重写
```

**不是在旧 JSON 后面添加第三轮，而是重新写出包含三轮的新 JSON。** 副作用工具执行前的检查点，也走这条完整快照保存路径，不仅是每轮结束时保存。

依据：`TinyHarness.Core/Services/Persistence/SessionStore.cs:413`。

另外，前面说的**旧 run 快照**才是每次运行另留一个文件；它与 v3 同时写入，造成了额外重复。

#### Codex：向会话记录中追加

正常写入更接近：

```text
已有记录：第一轮相关记录
追加：第二轮相关记录
追加：第三轮相关记录
```

恢复时，再根据这些记录以及压缩检查点重建当前上下文。压缩检查点本身可能包含替代历史，所以也不是“永远只写增量、绝不重复任何内容”。

#### 是不是最大的区别？

**就我们正在讨论的持久化架构而言，是最根本的区别：**

- **v3 保存“当前完整状态是什么”。**
- **Codex 主要记录“会话依次发生了什么”，再据此恢复状态。**

这会进一步影响长会话的写入量、历史追查和恢复方式。但它**不直接决定中断恢复是否安全**；副作用执行意图、结果确认、保存失败处理，仍然需要单独设计。

还有一点很重要：**完整快照本身不是坏设计。** 它简单、读取恢复直接，也容易校验。当前明确的问题是完整快照被两条路径重复保存；是否进一步改为 Codex 式追加日志，则是另一层架构选择。

### 12. 长期使用是否更适合 Codex 的方案？

**用户：**

> 从长远角度来看呢，会不会因为项目、会话太多，导致快照保存的太多了。虽然我觉得不要过度设计但codex的
> 方案确实还行？

**助手：**

**从长远看，我更倾向于采用 Codex 那种“追加记录＋压缩检查点”的方向。对于你要长期日常使用的 coding agent，这不算过度设计，而是在核心存储上选择更合适的增长方式。**

不过，需要把两种增长问题分开。

#### 1. 会话数量多，不是完整快照独有的问题

如果有一千个会话，v3 正常情况下就是一千份当前会话快照，而不是每保存一次就永久多留一份。

Codex 也要保存这一千个会话的记录。因此，**项目、会话数量增长带来的总存储量，两种方案都要面对**，最终都需要列举、归档、删除等生命周期管理。

追加日志也不会天然更省空间：它保留历史变化，压缩检查点还可能重复保存部分上下文。

#### 2. 真正不利的是单个会话越来越长

v3 每次保存都重写完整历史，而且副作用执行前的检查点也要保存。

假设一个会话逐渐增长，每次新增内容大致相同：

```text
第一次写入 1 份内容
第二次写入 2 份内容
……
第 N 次写入 N 份内容
```

最终文件只有 N 份内容，但**累计写入量是 1＋2＋……＋N**。长会话中，反复序列化和写入旧历史的成本会越来越明显。

目前还有两个具体因素：

- **旧 run 快照继续逐轮留档**，导致完整历史的多个前缀真的被长期保存。这是当前应消除的重复。
- **v3 快照有 16 MiB 上限**。现有上下文压缩只缩小发送给模型的视图，不删除本地完整历史，所以不能靠模型压缩避免最终触及这个上限。

这些比“项目多了会不会文件太多”更直接。

#### 3. 为什么 Codex 的方向更适合长期使用？

追加式记录的优势不是文件数量少，而是：

- **正常写入主要与本次新增内容有关**，不必反复重写旧对话。
- **执行事实可以就地记录**，不必等到回合结束才生成一份完整结果快照。
- **历史变化有据可查**，压缩、取消和回合结束可以作为明确记录保存。
- **压缩检查点让恢复不必永远从头重建**，可以读取检查点及其后的记录。

代价是恢复逻辑和故障处理比单个快照复杂，尤其要认真处理半条记录、顺序、重复写入和未知副作用。**JSONL 只是文件形态，不会自动解决这些问题。**

#### 我的取舍

**值得采用 Codex 的核心存储模型，但不值得复制它全部的产品基础设施。**

对 TinyHarness，合理的复杂度是：

- 统一的追加式会话记录。
- 明确的协议内容、执行事实和压缩检查点。
- 共用的读取与恢复逻辑。
- 保留当前未知副作用阻断和脱敏边界。

现阶段不必同时引入 SQLite、复杂分叉引用、历史分页服务或自动归档系统。那些可以由实际使用规模推动。

**所以，我不建议仅因为当前 v3 已经完成，就继续围绕完整快照长期扩展。你的目标本来就是长会话、可恢复、日常使用，追加式记录是与目标相称的基础设计；真正的过度设计，是把 Codex 为更大产品规模建设的所有配套也一起搬进来。**

## 二、更正后的事实与结论

以下为便于后续阅读的归纳，不替代上面的对话记录。

### 1. 术语不能混用

- **M7 旧运行存储**：单次运行审计 JSONL，加脱敏的 `.session.json` 检查快照。
- **M13 v1/v2/v3**：`PersistedSession.formatVersion` 的演进，不是 M7、M12、M13 各自的代称。
- **v3 canonical**：保真续聊协议内容；文件不加密，可能包含对话中的秘密。
- **v3 inspection**：脱敏后的回合／运行检查视图，不是另一套完整消息数组。
- **运行审计**：工具准备、权限、执行结果、usage 和压缩事件等。
- **会话提交审计**：用于快照提交序号对账，不等于运行审计。

没有发现严格意义上 M13 v1/v2 拥有、v3 却删除的功能。v2 缺少独立提交／发布的历史证据，不能把文档中的过渡方案描述成独立发布版本。

### 2. 当前实际重复的是两条全量快照路径

`chat` 同时使用 `FileRunRecorder` 与 `SessionStoreWriter`：前者按 run 留下完整脱敏历史快照，后者整体替换当前会话的 v3 快照。拆开旧记录器中的审计与快照职责，可以消除重复，不要求立即改变 v3 的存储模型。

v3 本身并非每次保存都永久增加一个快照文件；它重写同一个会话文件。副作用前检查点和终态保存都会发生完整序列化与替换。

### 3. “统一”不等于只允许一个文件

合理的审计、脱敏检查投影、索引和压缩检查点可以与会话记录并存。关键是明确各类事实的权威来源、派生关系及失败语义，不让两套可变状态各自决定同一事实。

Codex 自身也有协议项、展示条目、索引和 SQLite 状态，并非绝对去重。尤其 SQLite 不能整体描述为可随意删除、无损重建的纯缓存。

### 4. 追加式方案是讨论中的推荐方向，不是已批准的实施决定

助手最终更倾向于借鉴 Codex 的追加式会话记录、结构化执行事实和压缩检查点，原因是长期会话中的累计重写成本与恢复需求，而不是文件后缀或版本号本身。

用户尚未授权实施替换，也没有决定新格式名为 v4。当前 `PLAN.md` 的快照＋追加审计契约仍是现行计划；若选择改变权威存储模型，需要另行明确格式、兼容和验证契约，不能把本次讨论当作计划已变更。

### 5. 安全与兼容边界不能随存储模型一起静默改变

- 不自动重放旧工具，不把历史审批记录恢复为可执行授权。
- 保留执行意图、结果确认与未知副作用检查机制。
- 不完整工具组的协议处理与副作用是否已发生是不同问题。
- 保真协议内容不能用脱敏检查稿替代。
- 检查输出保持脱敏；新格式不天然提供加密。
- 原子替换、追加写入和普通 flush 都不能单独证明断电持久性或恰好一次执行。
- Codex 缺失结果的占位归一化、坏行跳过和普通工具前记录失败处理，不等价于 TinyHarness 当前的 `NeedsInspection` 与检查点门禁。

## 三、后续评估仍需决定的事项

这些是本次讨论留下的设计问题，不是本文件批准的实施步骤：

1. 仅收口 v3 的重复写入，还是采用新的追加式权威存储。
2. 如采用新格式，格式标识、旧 v3 的读取／转换契约与旧 run 行为如何处理。
3. 哪些执行事实进入规范会话记录，哪些作为独立审计或脱敏检查投影。
4. 压缩检查点的内容、写入时机与模型上下文重建规则。
5. 半条记录、重复写入、未知版本、损坏记录和保存失败的处理边界。
6. 长会话／多会话资源上限与生命周期管理；不把 SQLite、分页或复杂分叉当作先决条件。

- 重复或空工具调用 ID 在整轮执行前拒绝。进程树回收失败、sandbox 缺失终态或运行期协议损坏通过 `ToolExecutionUncertainException` 终止本轮，保留未知状态并阻止后续工具，不转为已确认失败。

### 2. 原 M12–M17 路线

## 10. 实施路线与纵向切片

沿用 M1–M11 历史编号，后续从 M12 开始。默认顺序如下；各切片包含直接相关测试，不集中到阶段末尾。

### M12：交互式多轮与宿主事件

**目标：不退出进程即可持续讨论和完成多个回合。**

1. M12.1：定义 Session / Turn / Run 的最小内存生命周期，演进现有 observer；保持 `run` 和 MCP 行为。
2. M12.2：贯通文本增量、工具/审批、usage/压缩与终态事件；脱敏、有界消费和单一 CLI 输入协调。更新交互模式审批文案，明确授权范围为本次运行而非长期会话，并说明旧 `[s]ession` 输入的兼容语义。
3. M12.3：增加交互入口，连续用户回合共享上下文；处理当前目标变化、Ctrl+C、EOF 与重复启动请求。

验收：fake 模型完成“解释 → 追问 → 要求修改 → 拒绝一个工具 → 完成”的多回合链；当前目标正确，旧事实不丢失，工具组完整，Responses 语义不退化；文本不会重复打印，取消后不执行后续工具，审批不串入用户 prompt。此里程碑先解决进程内会话，不宣称支持重启续聊。

### M13：版本化会话存储与安全续聊

**目标：正常退出后可继续，异常退出后不重放状态不明的操作。**

1. M13.1：受保护存储、格式版本、原子快照、提交序号、排他写入和严格离线 list / show；旧快照只读兼容。
2. M13.2：完整回合的保存与续聊，工作区/模型/协议检查、canonical 保真存储（检查投影与审计保持脱敏）与 opaque 数据完整性契约。
3. M13.3：执行意图/确认记录、中断判定、最近完整边界恢复与 NeedsInspection 阻断；沿用 v3 两层表示，以校验后的 canonical 历史构建模型续聊视图，以脱敏检查投影呈现中断事实。

验收：保存后重启并追问仍保留目标、事实与必要协议内容；在准备、批准、写入、结果回传及落盘边界注入故障，均不重复写入/执行、不复活批准、不制造工具结果；损坏/未知版本/并发/存储失败拒绝得当；恢复管理操作不调用模型或工具。opaque 恢复不满足门槛（完整性哈希不符或内容曾被脱敏）时明确拒绝无损续聊，不伪造原值；回合/运行检查投影、审计与终端输出的已知密钥脱敏不因 canonical 保真而关闭。M13.2 v3 快照已通过离线回归、NativeAOT 发布与仓库外模拟服务续聊验证；M13.3 中断结算、阻断与确认链已通过离线回归、NativeAOT 发布与仓库外原生产物验证（含阻断保持、确认解除与确认后免阻断重启）；真实模型 chat 与真实续聊（含中断后确认）尚未验证。

### M14：项目指令与只读/实施模式

**目标：理解项目约定，但由宿主决定可做什么。**

1. M14.1：根及局部 `AGENTS.md` 发现、作用域、内容变化检测和上下文预算。
2. M14.2：Analyze / Implement 宿主强制能力，显式切换及旧 `run` 兼容。
3. M14.3：目录作用域变更与续聊重新加载，待执行计划失效/重准备，用户可检查生效指令。

### M15：任务控制与运行预算

**目标：长任务可以纠正、暂停或取消，不会无限消耗。**

1. M15.1：稳定工作项、状态来源和当前目标；与 StructuredState/压缩保持一致。
2. M15.2：安全边界暂停、补充指令队列、继续及取消；取消后新运行明确建立。
3. M15.3：墙钟、step、工具和累计 token 限额、有界模型重试、预算展示与终态。

验收：模型调用、等待审批、工具执行和压缩阶段均覆盖取消/控制；暂停不遗留无管理进程，不改变已审批计划；重复控制命令幂等；普通与摘要模型请求计入预算；超限和断流不会触发未完成的工具调用；恢复后不清零会话累计统计来隐藏历史消耗。

### M16：只读 Git 检查与验证交付

**目标：用户能够核实到底改了什么、验证了什么。**

1. M16.1：有界只读 Git status / diff、开始基线与已有修改记录；非 Git 降级为文件证据。
2. M16.2：工具执行/补丁记录与实际工作区差异关联，处理并发和 shell 修改的归因歧义。
3. M16.3：确定性运行报告、模型解释与终端/结构化产物，不增加模型自行声明验证成功的通道；报告与可分享的报告 artifact 使用脱敏检查输出，不直接导出 canonical 会话内容或 opaque 载荷。

验收：初始 dirty 仓库、未跟踪文件、外部并发修改、测试失败/未执行/输出截断和取消均被准确报告；只读 Git 不触发外部程序或修改仓库；报告不把历史通过当作当前通过，也不补造测试数量；查看报告不调用模型。含已知测试秘密的会话、命令输出与模型解释经终端、结构化报告和报告 artifact 输出后，均不能泄漏该秘密或 opaque 原文，且不得影响 canonical 内容的恢复保真性。无自动 Git 写操作。
