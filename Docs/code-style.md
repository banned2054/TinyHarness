# .NET / C# 代码排版约定

本文件记录用户明确表达、需要结合语义和函数整体布局判断的 C# 排版偏好。
机械格式继续采用项目的 `.editorconfig` 与 solution team-shared `.DotSettings`；这里不是另一份工具配置，
也不声称这些偏好全部无法通过工具表达。AI 应在写代码和检查实际 diff 时落实这些约定。

用户当前明确要求优先于历史样本。已有源码含多种排法，不能把工具自动换行、过去 AI 的写法
或个别例外全部推断为用户有意选择。不借排版改变可观察行为、拆方法、添加临时变量或扩大修改范围。
在当前授权范围内，可以按本文做提前返回、属性模式匹配等保持行为的可读性整理；它们属于语法和控制流整理，
不能笼统称为纯空白格式化，也不能仅以 formatter 已运行作为完成依据。

## 1. 先看整个函数，再决定在哪里换行

- 默认保持相关表达式的整体性；短而清楚的调用、访问链、条件不主动拆成多行。
- 换行是为了看清结构、分组或满足有效行宽，不是为了让每个 token 或每次调用各占一行。
- 同时考虑函数的纵向长度、续行的起始列和横向空间。不能只看某一行是否低于字符上限，
  也不能为了减少行数把长表达式强行挤回一行。
- 不擅自另定一个统一字符数代替审美判断。遵守当前有效设置的行宽；行宽足够也不代表一行
  塞下所有逻辑就更易读。
- 空行用于区分执行阶段和逻辑段落，不在每次调用或简单语句后机械添加。
- 用户主动选择的折行应尽量保留，尤其是折行后右侧能完整呈现的赋值或返回表达式。
  不确定时结合相邻布局判断，不为了统一形状反复拆开又合并。

## 2. 调用参数：首参数靠近左括号，后续参数对齐

普通调用能清楚放下时，首参数和左括号保持同行；不默认在左括号后立即换行。
需要多行时，后续参数与首参数对齐，不替换成另一套统一缩进，也不无故再向右缩进。

```csharp
var result = CreateResult(sessionId, turnId);

var result = CreateResult(sessionId,
                          turnId,
                          executionRecords,
                          cancellationToken);
```

调用默认不在左括号后立即换行；构造函数、嵌套调用也一样。先尝试将整个调用移到赋值或返回表达式的下一行，
再判断参数是否需要换行。不要只为迁就工具生成的缩进，就把首参数单独推到下一行。
多行 lambda、集合表达式或确实无法容纳的长表达式可以例外，不能将例外套用到普通调用。

函数定义可以在左括号后换行。此时重新利用下一行的横向空间：参数能清楚放在一行就放一行，
不沿用原先被长函数头挤出来的逐参数换行。仍放不下时再分组或逐参数对齐，不能把多个已经能合并的短参数机械拆开。

```csharp
private static Task SaveAsync(
    Session session, Context context, CancellationToken cancellationToken)
{
    // ...
}
```

用户明确保留的布局和有效设置要求的被动折行可以例外；判断时同时看函数定义与函数体。

参数列对齐可能占用较多横向空间，保留这项偏好。但如果整个右侧因此被挤得支离破碎，
可以在赋值右侧或返回表达式开始处选一个自然断点，再让右侧保持完整：

```csharp
var executionResult =
    CreateResult(sessionId, turnId, executionRecords, cancellationToken);
```

是否使用这个断点由当前函数的布局决定，不自动把所有赋值改成两行。

## 3. 成员访问与链式调用：按语义分组，不做阶梯

短的 `A.B.C` 保持完整；不能仅因存在多个点号就拆行。

```csharp
var name = session.Model.ModelId;
var ids  = records.Select(record => record.Id).ToArray();
```

较长的链按语义步骤或步骤组换行。不要强制每个访问、每个短调用、每个终结调用都独占一行，
也不要把续行逐层推向右侧。换行后相邻的点号保持稳定对齐；默认参考已有代码的行首点号，
这只是既有排法的参考，不把用户未明确指定的所有点号细节上升为硬规则。

```csharp
var ordered = documents.OrderBy(document => Depth(document.ScopeDirectory))
                       .ThenBy(document => document.SourcePath, StringComparer.Ordinal).ToArray();
```

`ThenBy(...).ToArray()` 可以作为同一语义组保留，不需要为了整齐强拆 `ToArray()`。
同理，`await`、调用、参数及 `.ConfigureAwait(false)` 应一起考虑：能连贯放下时保持完整，
确实太长时选自然边界，不机械拆散为多个越来越靠右的片段。

## 4. 长条件：一行一个条件，连接符在行尾

短条件仍保持一行。一旦因为长度或可读性拆行，默认每行一个完整逻辑条件，
将连接下一条件的 `&&` 或 `||` 放在上一行末尾，续行条件对齐：

```csharp
if (hasSession &&
    matchesIdentity &&
    hasCompleteHistory &&
    isWithinBudget)
{
    ContinueRun();
}
```

不要把连接符改到行首，不在已经拆行时为了填满行宽又把多个独立条件塞回同一行。
这里的“一个条件”指可独立理解的条件单元，不是把条件内部的方法参数也全部拆开。
有混合 `&&`／`||`、括号、模式匹配或注释时，先保持原有分组、优先级和短路语义，
再在同层条件边界折行；不能为了排版增删分组或重新排列条件。

## 5. 简单方法与初始化器

方法体只是一个简单 `return`、且没有需要保留的语句块、指令或说明时，优先使用 `=>`。
不要为了使用表达式体把多步骤方法压成复杂表达式，也不要删掉有意义的局部说明。

返回对象初始化器时，能放下的函数头和 `=> new()` 保持同行，花括号和属性采用正常块缩进；
不要让整个初始化器跟着表达式起始列移到屏幕右侧：

```csharp
private static Options CreateOptions() => new()
{
    Model         = "example",
    MaxAgentSteps = 8
};
```

同一小组内的类型、变量、赋值或属性可保留已有列对齐；不要跨不相关的逻辑段落为了对齐
制造大片空白。函数头或表达式确实过长时允许折行，不为追求这个示例的形状牺牲可读性。

## 6. 提前返回，减少不必要的嵌套

当一个条件块包含函数剩余的主要工作，而不满足条件只需返回时，优先反转条件、提前返回，
让正常路径少缩进一层。循环中适用时可以使用 `continue`。

```csharp
if (!shouldSave) return;

await SaveAsync(session, cancellationToken);
PublishSaved();
```

已有分支以 `return`、`throw` 或 `continue` 结束时，检查后面的 `else` 是否可以直接展开。
不是把每个短 `if` 都改成守卫语句；两个分支同样重要时可以保留原结构，也不为提前返回复制公共尾部代码。
保持返回值、条件求值顺序、异常与取消语义一致，不跨越 `lock`、`using` 或 `try/finally` 移动工作和资源释放。

## 7. 同一对象的属性条件，优先考虑属性模式匹配

对同一稳定对象连续判断多个属性的常量、关系或空值条件时，优先考虑属性模式，减少重复访问链，
把同一对象的状态放在一起表达。例如：

```csharp
if (item is { Enabled: true, State: WorkState.Ready })
{
    Execute(item);
}

if (result is { Status: RunStatus.Completed, Budget: { ModelRequests: 3 } })
{
    Accept(result);
}
```

条件短时模式保持一行；较长时按属性折行，不拆散 `Type.Member` 或嵌套属性的语义单元。
模式不能表达的一般计算、方法调用或变量间比较保留普通条件，不追求把所有条件塞进一个模式。
转换前确认空值、短路和求值次数等价：属性模式对 null 返回 false，不能悄悄替代原本会抛异常的访问；
含副作用的 getter、可变访问链或重载比较不能机械合并。

## 8. using 与工具清理的分工

用户偏好命名空间按字母顺序排列，不把 `System` 自动提升到最前。使用工具前，核对该项目
实际的 cleanup profile；保留 using 原顺序不等于已经执行字母排序。
不要为运行清理擅自替换项目选定的 profile，或把 using 重排夹带到不相关修改。

工具清理之后，AI 仍需逐个看整个受影响函数和前后 diff，检查调用首参数是否被无意义换行、
定义参数能否合并、链式表达式是否被拆散、参数列是否过度占用横向空间、条件是否一行一个、
初始化器是否整体向右漂移，以及是否有适合提前返回或属性模式匹配的条件。
纯空白整理与 `return` 转表达式体等语法清理分别核对，不能把所有 cleanup 都称为纯格式化。

遇到嵌套调用或长表达式的排版纠结时，采用日常处理方式：先把该表达式已有的人工折行收编成一行，
再使用项目选定的 ReSharper profile 格式化一次，让工具重新决定断点与对齐。收成一行是格式化的输入，
不是要求最终代码保持单行；不将整个文件、语句块、注释或字符串内容机械合并，也不改变代码语义。

对调用表达式，重点检查首参数仍紧跟左括号，不在左括号后立即换行；函数定义的换行仍按第 2 节处理。
在满足这一点和有效 `.editorconfig` 的前提下，接受 ReSharper 产生的续行、深列对齐和必要的链中折行，
不再仅因其不符合第 2、3 节的人工布局建议而与工具反复拉扯，也不据此宣称存在必须解决的格式冲突。
不为消除这类排版引入局部变量、块 lambda、方法提取或共享设置修改。

工具清理后的人工检查仍需进行，尤其是工具无法判断的语义分组、注释、长条件及改动范围。
发现左括号后立即换行时，先在该表达式范围重新收编并格式化、检查结果；若仍不能满足要求，
如实指出具体位置，不静默修改共享设置，也不不断重复清理使人工排版来回变化。
